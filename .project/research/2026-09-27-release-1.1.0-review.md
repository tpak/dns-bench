# Pre-release review of v1.1.0

- **Date:** 2026-09-27
- **Question:** Before tagging v1.1.0, the first release published by `release.yml`, were the
  release notes accurate and complete, would the untested tag-push path work, and was the version
  consistent everywhere?

## Method

A workflow of 6 agents:

- **Three independent reviewers:**
  - release notes against `git log` and `git diff v1.0.0..HEAD`;
  - the tag-push path of `release.yml` and `ci.yml`;
  - version consistency, plus the full validation gate.
- **One adversarial verifier per reviewer:** it tried to refute every finding.

No finding was refuted. Two verifiers corrected a proposed fix.

## Verified facts worth keeping

- **Tag filter:** in GitHub filter patterns only `* ** ? + [] !` are special. So `.` in
  `v[0-9]+.[0-9]+.[0-9]+` is literal, and the pattern matches `v1.1.0`.
- **ci.yml on tag pushes:** it has only a branch filter, so it does not run for tag pushes. On a
  tag push it runs only as release.yml's reusable workflow.
- **Protection:**
  - ruleset 24071666 ("main") applies only to the default branch;
  - ruleset 24071611 ("main protect") is disabled and duplicates two of its rules;
  - neither affects pushing a tag or creating a release.
- **`require_extra_approval_for_unattributed_changes`:** GitHub defaults it to `true` when a
  ruleset payload omits it. A PR then needs one extra approval if it has commits whose author
  email isn't linked to a GitHub account. Commits here use `tpak@users.noreply.github.com`, so the
  rule never applies.
- **Browser support:**
  - `Object.hasOwn`: Chrome/Edge 93, Firefox 92, Safari 15.4.
  - `color-mix()` (already in 1.0.0): Chrome 111, Firefox 113, Safari 16.2. Without it the
    declarations are dropped: some tints and focus shadows go, and the progress spinner vanishes.

## Recommendation

For future releases, check the notes against the diff before tagging. A GitHub release is
published once and read on its own, and this review found two medium inaccuracies in notes that
looked fine.
