# Pre-release review of v1.3.0

- **Date:** 2026-09-29
- **Question:** Before tagging v1.3.0 (Phase 8, measurement validity), are the release notes true
  and complete, do upgrading and going back work, and does anything break for users?

## Method

A workflow of 16 agents: nine narrow, time-boxed checks, each followed by an adversarial verifier
for its findings, then a completeness critic. Each agent worked in its own scratch clone. The
checks:

- **notes-a, notes-b:** the release notes, claim by claim.
- **notes-completeness:** the whole `v1.2.0..RC` diff, compared with the notes.
- **compat-files:** 1.0.0 and 1.2.0 run files in 1.3.0, and 1.3.0 files in 1.2.0.
- **api-cli-shape:** the JSON shapes of 1.2.0 and the RC, diffed.
- **mechanics:** version, notes extraction, release.yml checks, and the gate in a clone.
- **live-smoke:** real queries, the CLI, and `serve`.
- **ui:** headless Firefox, every view plus "All runs combined".
- **docs:** the README against the code.

Result: no high findings. mechanics, live-smoke and ui were clean. There were 29 findings (all
confirmed or partly confirmed, low or medium), which reduce to about 17 distinct issues. The
critic found one more, medium, that it reproduced on macOS.

## Findings and what was done

| Finding | Severity | Disposition |
|---|---|---|
| On macOS a LAN resolver that goes down makes `send()` fail with "Host is down" or "No route to host"; those were classed as local errors, so its failure rate read about 0 % (critic) | medium | `stats.failure_kind` treats those two strerror texts as `network` wherever they appear, which also reads older files. "Network is unreachable" stays local. Tests updated on purpose. |
| The low-samples note counted repeats and said "run more rounds", which the first-answer change makes useless | medium | It counts first answers now. The advice is "add domains, or combine runs"; in a combined view it says "combine more runs" instead of pointing at itself. |
| "Every latency figure uses first answers" is false for per-server figures, which use each server's own first answer (they can include cache hits the sibling caused) | medium | Documented in the notes and the README. The code stays: resolver-level first answers could leave one server with none. |
| A resolver whose failures count in its score could still be called "tied" with the best ("a good choice") | low | Ties now also require the score to count both sides' rates alike. |
| A server that failed only locally showed "fail 0.0%"; `n` still counts local errors | low | Shown as `-` in the report and the UI. The Queries line lists local errors. The notes and README say `n` = `ok` + `failures` + `local_errors`. |
| The first-answers note asserted repeats came from the cache even when they weren't faster | low | Reworded to what is always true. The UI says "may be cached". |
| The UI tie text said "either" with several ties; the histogram mixed in repeats without saying so | low | "any of them" when there are several ties, and the histogram subtitle says repeats are included. |
| The notes omitted: new note codes and the `counted` param, `*` in the report, the Local column, `backup_tied_with`, `median_ci`/`p95_ci` on ranking entries, a whole-`null` interval, "exact" holding only up to 10,000 answers, the retry condition of a tie, `n` including local errors, and History medians changing | low | Notes and README rewritten. The intro now says whose 13 runs they were, and that yours may differ. |
| The README's `tries` row said a retry "is penalised in the score" unconditionally | low | Fixed. |

**Checked and fine:**

- Old files load everywhere: 1.0.0 and 1.2.0 files load in 1.3.0; 1.3.0 files and a mixed
  folder load in 1.2.0; config.json is byte-identical in both directions.
- The notes extraction gives exactly the section.
- The live CLI and `serve` produced no tracebacks.
- Every view renders, and the footer shows 1.3.0 and analysis v2.
- Performance is about 1.4× v1.2.0: 0.52 s to combine 30 runs × 2,160 rows.

**Verified by hand:**

- A failure rate starts counting at 3–9 failures against a resolver with none (5 when both have
  the same number of queries).
- On the 13 saved runs, the recomputed resolver medians went up in 42 cases, down in 19 and stayed
  the same in 3.

## Decision/recommendation

Release 1.3.0 with these fixes. **Not done, noted for later:**

- "All runs combined" can't be reached by URL (the dataset lives only in UI state).
- The screenshot harness needs an absolute `--screenshot` path in some sandboxes (fixed in that
  note).
- Linux behaviour for a dead on-link host (expected on `recv`, which is classed `network`) wasn't
  tested live.
